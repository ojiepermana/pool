# Changelog

All notable changes to this project are documented in this file.

and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Conservative clean session reuse on the primary path, with identity and generation isolation, bounded rollback/reset quarantine, startup validation and physical backend budgets across global, node, database and login scopes. Unknown SQL or startup profiles retain dedicated connections (spec 0005).
- Idle age, backend lifetime, cleanup and client write limits, plus credential-only SIGHUP rotation with atomic publication and retirement of old idle, waiting and connecting generations (spec 0005).
- Resolved standard library capability checks, locked workspace dependency checks, exact native build settings, private-key header protection and NOTICE version checks, with targeted fault-injection proof cases (spec 0005).

- A Cargo workspace with two packages: the `pool` daemon binary in `apps/pool` and the `pool-config` library in `crates/pool-config`. Rust 1.100.0 is pinned by `rust-toolchain.toml`, and `unsafe` code is forbidden in both packages (see spec 0001).
- `pool check-config --config <PATH> [--format human|json]`, an offline command that accepts or rejects a configuration file before you start POOL. It opens no socket, starts no thread and reads at most 1 MiB plus one byte of the file.
- The first configuration contract: `config_version = 1` plus two reserved tables, `result_cache` and `automatic_promotion`. Leaving them out, or setting `enabled = false`, is valid. Asking for either one is refused with `config.unsupported_capability`, because neither capability exists in this build (SEC-10).
- A fixed set of finding codes for rejected files, such as `config.syntax`, `config.schema`, `config.missing_key`, `config.unsupported_version`, `config.too_large` and `config.not_utf8`, with a line and column where the parser gives one. The output is built only from constant text, schema key names and positions, so nothing you put in the file, a secret included, can appear in it (SEC-11).
- A JSON report (`--format json`) that is one line with a fixed field order, for scripts.
- An exit status convention for POOL commands: 0 for success, 1 when the input is rejected, 2 for a usage error, 3 when the command could not finish, for example when the file is missing or cannot be read.
- `pool --help` and `pool --version`.
- Fifteen configuration fixtures and 134 automated tests that cover every acceptance criterion of the first build on the workstation. On Linux 136 tests run, because two of them need `/dev/full`.
- Workspace build notes, acceptance criteria `0001 AC-1` to `AC-13` and a five step build plan in spec 0001, a verification record (`docs/specs/0001-initial-architecture/verify.md`) and an independent review (`docs/reviews/2026-11-14-scope-001-stack-and-workspace.md`). The Linux container build (`0001 AC-2`) passed for `aarch64-unknown-linux-gnu`, the one declared Linux target, and the verification record holds the image digest and the binary checksum.
- Three shared conventions in the engineering standards: configuration keys, exit status with command output, and log event fields with redaction.
- `scripts/check.sh <name>`, one command for each check, and the same command that CI runs. The names are `fmt`, `clippy`, `test`, `deny`, `guards`, `docs` and `linux-build`, plus `fuzz`, `sbom` and `tools`. `scripts/check.sh all` runs the first six and keeps going after a failure. It exits 0 when a check passes, 1 when it fails, 2 for a name it does not know and 3 when a tool or the Docker daemon is missing (see spec 0002).
- A CI definition, `.github/workflows/ci.yml`, with seven jobs that each call `scripts/check.sh <job id>` on the 64 bit ARM runner `ubuntu-24.04-arm`. It runs on a pull request, on a push to `main` and once a day, asks for read access only, uses no secret and names each action by a full commit hash.
- A branch rule kept as a file, `.github/rulesets/main.json`, and a pull request template. The rule lets a change reach `main` only through a pull request whose seven checks passed, with a merge commit, and nobody is on the bypass list.
- A dependency policy in `deny.toml`, checked by `cargo-deny` 0.20.2 on the product lockfile and on the fuzz lockfile. The allowed licenses are exactly `Apache-2.0`, `MIT` and `Unicode-3.0`, with one exception, `NCSA` for `libfuzzer-sys`. Known advisories, unmaintained and unsound packages fail the check for direct and indirect dependencies, and no advisory is ignored (SEC-13).
- `pool-repo-check`, a small Rust program in `tools/repo-check/` with no dependencies, kept outside the Cargo workspace. `workspace` guards the package set of each lockfile, the paths and source text that must not exist, lint inheritance and the allowed dependencies between workspace packages. `ci` guards the shape of the workflow and the branch rule. `docs` checks local links and heading anchors, that the scope index and the feature files agree, and that requirement IDs stay defined. It has 198 tests.
- `scripts/linux-build.sh`, which runs the Linux build command of spec 0001. A guard fails when the script and the spec differ.
- `scripts/prove-checks.sh`, which applies twenty eight deliberately wrong changes to a private copy of the committed tree and requires each named check to reject its case.
- A fuzz target, `validate`, for `pool_config::validate` in `crates/pool-config/fuzz/`, run for 60 seconds by `scripts/check.sh fuzz` with `cargo-fuzz` 0.13.2 on the toolchain `nightly-2026-10-17`. It is a command, not a required check.
- `scripts/check.sh sbom`, which writes a CycloneDX inventory of the packages `pool` is built from to `target/sbom/pool.cdx.json` with `cargo-cyclonedx` 0.5.10.
- Spec 0002 with acceptance criteria `0002 AC-1` to `AC-20`, ADR 0002, a verification record (`docs/specs/0002-standards-and-tooling/verify.md`) and an independent review (`docs/reviews/2026-11-14-scope-002-standards-and-tooling.md`). The record holds the workstation evidence. The evidence from a real pull request is added to it when those steps have run.
- A reviewer roster in the engineering standards, with one row for each review role and what a fresh model may review in place of a person. Every role is `Not assigned` today.
- The tools adopted in scope 002 in the technology evaluation, and agent guides for `apps/pool` and `crates/pool-config` (`AGENTS.md` in each folder).
- Configuration keys for your clusters, nodes and identity map, checked by `pool check-config`: the tables `[control]`, `[[cluster]]`, `[[node]]` and `[[identity]]`. A cluster names its PostgreSQL system identifier and the node you expect to take writes (`expected_writer`). An identity maps one pair of verified principal and requested database to a cluster, a backend login, a backend database and a credential file. Every new table is optional, so `config_version` stays `1` and every file that was valid before is still valid (see spec 0003).
- Six finding codes for the new keys: `config.invalid_value`, `config.duplicate_id`, `config.unknown_reference`, `config.duplicate_endpoint`, `config.duplicate_identity` and `config.unsupported_value`. `routing_profile = "replica"` is refused with the last one, because replica sessions do not exist in this build.
- A fourth form of the finding line, for a finding inside a repeated table. It names the key and the place, for example `config.duplicate_id at node.id, line 18, column 6: an id is used more than once`. In the JSON report the same finding has `key`, `line` and `column` all set.
- An exact identity map lookup in `pool-config` (`ValidatedConfig::resolve_identity`). A pair that is not written in the file gets no route. There is no wildcard and no default entry (`0001 SC-3`, SEC-2).
- Identifier and generation types in `pool-config`: one type for each kind of ID, built only by a function that checks its syntax, and three durable counters (topology epoch, authority revision and start sequence) that advance by one and stop at the top of their range. Two different kinds do not compare, and the compiler enforces that.
- A third workspace package, the `pool-control` library in `crates/pool-control`. It holds the authority rules as plain functions that read no file, no clock and no socket: `classify_startup` tells a first start from a missing, unreadable, foreign or restored journal, `plan_bootstrap` says when a first bootstrap may happen, and `writer_admission` opens writes only when the configuration, the journal and a fresh observation all name the same writer (`0001 SC-8`, R-19). Nothing calls it yet. The first real write path of scope 004 does.
- Tests for the four written walks of spec 0003 (clean startup, missing journal, conflicting role evidence, and a backup restored after a promotion), and a model test that checks the answer and its reasons over 8192 combinations of configuration, journal and observations.
- A limit on validation time at the 1 MiB file limit. Three made files of almost 1 MiB, one of them invalid with one finding for each entry, each validate within 10 seconds in a debug build (`0003 AC-15`).
- A check in `writer_admission` that a ready authority still belongs to the configuration it was confirmed with. A configuration without `control.authority_id`, or with another value, closes writes (`0003 AC-16`).
- Thirteen new configuration fixtures, which brings the set to twenty eight.
- Spec 0003 with acceptance criteria `0003 AC-1` to `AC-16`, ADR 0003, a verification record (`docs/specs/0003-control-and-session-data-model/verify.md`) and an independent review (`docs/reviews/2026-11-15-scope-003-control-and-session-data-model.md`). The record holds the workstation evidence, a Linux container build and the seven checks on the pull request.
- The journal format (one SQLite file), the bootstrap rules and the contract of every control and session record, written down in spec 0003. They are specified here and built by later scopes. Nothing reads or writes a journal in this build.
- Ten glossary terms, among them Node, Journal, Authority ID, Bootstrap, Restore hold and Conflict latch.
- The first real path through POOL (see spec 0004). One client connects with TLS, proves who it is with `SCRAM-SHA-256`, is mapped to its own PostgreSQL login by the identity map, and reads and writes real data on the one node that the journal, the configuration and a fresh probe all name as the writer. The same SQL file gives the same output through POOL as it does directly against PostgreSQL 18 (`0004 AC-18`).
- Three new commands. `pool bootstrap` probes your nodes, writes the first journal and prints a new authority ID. `pool show-authority` prints the authority ID and the state of the journal. `pool run` is the daemon, and it takes no `--format`. `pool run` binds the listener only when the journal state is ready. In every other state it exits 1 with the finding of that state, one of six `authority.*` codes (`0004 AC-13`).
- Two new workspace packages. `pool-protocol` holds the wire format (startup packets, message headers and the SCRAM messages) and depends on no other package. `pool-core` holds TLS, frontend authentication, the backend connection, the session and the route view. `pool-core` and `pool-control` do not depend on each other, and `apps/pool` maps between them.
- The journal on disk: one SQLite file, `journal.sqlite3`, in a state directory that must have mode `0700`, with files of mode `0600`. A lock file lets one command at a time use the directory, and a second one exits 3 with `state.locked` (`0004 AC-9`, `0004 AC-10`).
- The probe and the control loop. The probe logs in as the monitor login of a cluster over TLS and reads the role, the system identifier and the timeline of each node. The control loop publishes a topology snapshot, and a session gets a route only while that snapshot marks the writer of its cluster open. A second primary sets a conflict latch in the journal, closes the cluster and ends its sessions (`0004 AC-12`, `0004 AC-14`).
- Configuration keys for a daemon that serves: the tables `[listener]`, `[limits]`, `[probe]` and `[[principal]]`, the monitor keys of a cluster and the TLS keys of a node. Every new table is optional, so `config_version` stays `1`. `pool check-config` accepts a file without them, and the three new commands report what they miss with `config.incomplete` (`0004 AC-5`, `0004 AC-8`).
- Two cross rules for the probe keys. `probe.observation_expiry_ms` must not be less than the period plus the timeout, and `probe.node_loss_timeout_ms` must not be less than twice the period plus the timeout. A lower value gives `config.invalid_value`.
- Finding codes for the new commands, each with constant text: `state.not_found`, `state.permissions`, `state.locked`, `secret.not_found`, `secret.permissions`, `secret.invalid`, `journal.failed`, `random.failed`, `listener.failed` and `runtime.failed`. They exit 3. A secret file with any group or other permission bit, or with another owner, is refused, and so is a certificate chain or a CA file that the group or others can write.
- The protocol subset of this build. TLS is required, so a startup packet without TLS gets `28000`. The protocol version is 3.0, and a request for a later minor version is negotiated down. After login POOL accepts `Query` and `Terminate`. Every other message ends the session with `0A000`. A `database` that is sent empty takes the value of `user`, as in PostgreSQL.
- A table of the SQLSTATEs that POOL itself sends, with constant message text that never holds a name, an address or text from PostgreSQL. An error that PostgreSQL sends during a query is passed on unchanged.
- One new backend for each session, closed when the session ends. A client that leaves inside an open transaction leaves no row, because PostgreSQL rolls the work back itself (`0004 AC-19`). When the answer to a COMMIT is lost, the client gets `08007`, the connection is closed and POOL never sends the statement again (`0004 AC-22`).
- A check that the server a session reaches is the server that was verified. Before a login succeeds, POOL asks the node for its system identifier, timeline and role on the connection of that session. Any other answer closes the backend with `08006` (`0004 AC-29`).
- Handling of a peer that vanished. Every socket has TCP keepalive on. When the writer gives the probe no answer for `probe.node_loss_timeout_ms`, POOL marks the node lost, writes `node.lost` and ends the sessions on it (`0004 AC-30`).
- Limits with tests on real PostgreSQL: sessions, sessions for each principal, handshakes, waiters for a backend, backends for each node, three deadlines and two size limits. With 32 sessions that stopped reading 256 MiB of rows each, the daemon stays below 96 MiB (`0004 AC-20`, `0004 AC-21`).
- Shutdown on SIGTERM or SIGINT. The daemon stops accepting, ends idle sessions with `57P01`, ends the others when they become idle or when `limits.shutdown_timeout_ms` has passed, and exits 0 (`0004 AC-25`).
- Log events of `pool run`: one JSON object for each line on stderr, with sixteen event names such as `daemon.started`, `admission.changed`, `probe.failed`, `node.lost`, `session.started` and `session.ended`. No line holds a password, a verifier, SQL text, a principal, a login, a database name, a host or a file path (`0004 AC-24`).
- `scripts/check.sh integration`, which starts PostgreSQL 18.7 from an image pinned by digest, runs thirty tests against it and removes every container it started. Without a Docker daemon it exits 3. `POOL_IT_FILTER` runs only the tests whose name matches, as an aid for a developer. The check has run on a workstation under `bash` and `dash`. The CI definition does not run it yet (`0004 AC-26`).
- A second fuzz package, `crates/pool-protocol/fuzz/`, with the targets `startup`, `frontend_message`, `scram` and `auth`, and `scripts/check.sh fuzz-tools`, which installs the fuzz tool and its toolchain when they are missing (`0004 AC-27`).
- The first runtime, TLS and SQLite dependencies: `tokio` 1.54.1, `rustls` 0.23.46, `tokio-rustls` 0.26.6, `aws-lc-rs` 1.19.0, `rusqlite` 0.42.0 and `tracing` 0.1.44. With them comes the first native code in the product. `.cargo/config.toml` makes every build compile AWS-LC and SQLite from the source inside the locked crates, and a `NOTICE` file names SQLite 3.54.1 and AWS-LC 5.12.0 with their terms.
- Thirteen new configuration fixtures, which brings the set to forty one.
- Spec 0004 with acceptance criteria `0004 AC-1` to `AC-30`, ADR 0004, a verification record (`docs/specs/0004-one-real-primary-path/verify.md`) and an independent review in three rounds (`docs/reviews/2026-11-16-scope-004-one-real-primary-path.md`). The record holds the workstation evidence and a Linux container build. The evidence from a pull request is added to it when those steps have run.

### Changed

- The root `Cargo.toml` now denies the Clippy lints `dbg_macro`, `print_stderr`, `print_stdout`, `todo` and `unimplemented` for the whole workspace. No source file had to change.
- `CONTRIBUTING.md` and `README.md` name `scripts/check.sh` and describe the pull request path a change takes to `main`.
- Planning documents that still said no workspace existed now match the tree: the engineering standards, the implementation order, the repository structure, the testing strategy and the documentation index.
- Spec 0001 marks its follow ups on CI and automatic guards as answered by `0002 AC-5` and `0002 AC-6`.
- The workspace has three packages. `pool-repo-check workspace` knows the new package and the one allowed dependency, `pool-control` on `pool-config`, and rule W4 now also fails when `Cargo.lock` holds a local package that is not a listed workspace member.
- Proving case 17 of `scripts/prove-checks.sh` now changes the first line of the scope 004 file, because feature 3 is no longer `planned`.
- The word node now means a configured PostgreSQL server everywhere. Backend keeps its glossary meaning, a connection that POOL opens. The glossary rows "Observation" and "Approved writer" were reworded to match.
- The shared conventions in the engineering standards now hold the rule for identifier and generation types, and the engineering standards and the repository structure name the third package.
- Specs 0001 and 0002 carry dated notes that point at spec 0003: the first secret reference key (`identity[].credential_file`, read in scope 004), the fourth finding line, the new finding codes, the current shape of the workspace, and the answer to the open question on how the guards learn the packages.
- The workspace has five packages. `pool-control` now reads and writes the journal, and `apps/pool` calls its authority rules, which nothing called before. Only `crates/pool-control/src/journal.rs` may name `rusqlite`.
- The dependency policy in `deny.toml` has five exceptions by package for the licenses `ISC` and `BSD-3-Clause`: `aws-lc-rs`, `aws-lc-sys`, `rustls-webpki`, `untrusted` and `subtle`. The general list of allowed licenses is unchanged. `scripts/check.sh deny` now checks the product lockfile and both fuzz lockfiles.
- Rule W3 of `pool-repo-check` reads its forbidden source text from a baseline file with lines that deny and lines that allow, so the runtime and the socket types are accepted only where spec 0004 puts them. Rule W1 has a baseline for the new fuzz lockfile, and rule W6 lists four lockfiles.
- `scripts/prove-checks.sh` now applies thirty six wrong changes, up from twenty eight.
- `scripts/check.sh fuzz` runs every target of both fuzz packages, five in all, for 30 seconds each. `POOL_FUZZ_SECONDS` changes that time. Before, it ran one target for 60 seconds.
- `pool check-config` keeps the first 20000 findings and counts the rest. A longer report ends with `findings omitted: <n>`, or carries `"findings_omitted"` in the JSON form. A report with 20000 findings or fewer is unchanged (`0004 AC-7`).
- A name or a path that holds a control character, or one of the direction and separator characters that spec 0004 lists, is refused with `config.invalid_value` (`0004 AC-6`).
- `pool --help` lists the four commands.
- The fixture `invalid-unknown-key.toml` names its unknown table `no_table`, because `listener` is a known table now.
- Spec 0003 gained the criteria `0003 AC-17` to `AC-19`, and specs 0001, 0002 and 0003 carry dated notes that point at spec 0004.
